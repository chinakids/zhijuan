# 织卷 · 模型适配接入层 + 创作上下文装配（2026-09 定，本次落地）

> 主人指示：模型层面要有适配接入层——除本地模型外，对接各家（glm / deepseek / claude / gpt / gemini）远程 API；**harness 默认生效、不再有额外开关**；并检查 harness 上下文管理是否满足创作要求、相关上下文是否在创作时注入——不完善就设计完善落地。
> 本文件先讲清现状、设计、落地边界，再给改动清单与验证。

## 一、现状核查（动工前先回答主人两个问题的实情）

### 1. 模型层现状：只有一根本地 vLLM，且写死

- `AppSettings.llm = { baseUrl, model, apiKey }` 单端点；`runtime.ts` 只认识 `local-vllm` 一个 provider，设置不同就生成 `run/llm.override.patch.yml` 覆写它。
- 底层的 dsh 写作引擎（`dsh-llm-pi-ai` → pi-ai）本身支持多协议多厂商（openai-completions / openai-responses / anthropic-messages，厂商目录含 deepseek/anthropic/google 等），**适配能力在引擎层就在，织卷没利用**——需要一层「厂商预设」把各家 endpoint / 协议 / key 环境变量 / 模型清单管起来。

### 2. harness 上下文管理：**不满足创作要求（结论）**

- harness（默认引擎）的 `runChat` 每次只给模型：人设一句 + 环境块（作品根目录 + 当前章节路径）+ 最近 20 条对话历史 + 引用块 + 用户提问。**创作所需的相关上下文一个都没注入**：当前章正文、上一章尾部、涉及人物档案、世界观切片、素材索引……全要模型自己用 zj_* 工具去读（多轮、慢、且模型可能图省事不读就猜）。
- 渲染层存在一个 `buildAgentContext`（当前章 + 人物 + 切片 + 素材索引），但它**只在 legacy 直连引擎里用**，harness 根本走不到。模块设计 §11.1「发给模型的系统侧写自动带上」在 harness 下是落空状态。
- 结论：**需要把上下文装配移到主进程、并真正注入 harness 的创作路径**（含 sync 同步路径），legacy 直连就此退役。

## 二、设计

### A. harness 默认生效，去掉引擎开关

- 删除 `AppSettings.agentEngine: 'harness' | 'legacy'` 及其 UI 切换；harness（dsh 写作引擎）是唯一创作引擎。
- 删除 renderer `features/agent/llm.ts`（streamChat）与 `features/agent/context.ts`（旧装配），`sliceSync.ts` 的 legacy 分支一并删——**直连路径自此无消费者**，不留死代码。
- 设置里保留：服务商选择（即「用哪个大模型」）、「任务清单开关」与「提问开关」；写作引擎实时状态行。

### B. 模型适配接入层（providers.ts）

主进程用 **src/shared/providers.ts**（与渲染层设置页共用同一张厂商预设表，避免两份定义漂移），一张**厂商预设表**（模型适配层，对 dsh 唯一的接触面）：

| id | 名称 | 协议(api) | 默认 baseURL | key 环境变量 | 默认模型（可改） |
|---|---|---|---|---|---|
| local | 本地 vLLM（默认）| openai-completions | http://127.0.0.1:8888/v1 | LOCAL_LLM_KEY | deepseek-v4-flash-0731 |
| deepseek | DeepSeek | openai-completions | https://api.deepseek.com/v1 | DEEPSEEK_API_KEY | deepseek-v4-flash / deepseek-v4-pro |
| glm | 智谱 GLM | openai-completions | https://open.bigmodel.cn/api/paas/v4 | BIGMODEL_API_KEY | glm-5.3-flash |
| openai | OpenAI GPT | openai-completions | https://api.openai.com/v1 | OPENAI_API_KEY | gpt-5.6 / gpt-4o-mini |
| claude | Anthropic Claude | anthropic-messages | https://api.anthropic.com | ANTHROPIC_API_KEY | claude-sonnet-4-5 / claude-haiku-4-5 |
| gemini | Google Gemini | openai-completions | https://generativelanguage.googleapis.com/v1beta/openai | GOOGLE_API_KEY | gemini-2.5-flash / gemini-2.5-pro |

要点：
- **模型型号按 2026-09 官方文档核实**（glm-5.3-flash、deepseek-v4 系、gpt-5.6、gemini-2.5 系稳定向），但全部可编辑，适配层不绑定型号。
- 各家 `compat`（supportsDeveloperRole / maxTokensField）按适配差异配置；Claude 走 anthropic-messages（x-api-key），其余走 openai-completions（Bearer）。
- `buildLlmOverrideYml()` 按「当前活跃 provider 的预设 + 用户覆盖（baseUrl/model/apiKey）」生成一篇 `run/llm.override.patch.yml`（provider 路由 + agent-default-model），**默认本地也写**（幂等）——切换服务商 = 一套配置交给引擎重启（既有机制）。
- 设置结构：
  ```ts
  llm: {
    active: 'local'            // 当前服务商
    providers: { [id]: { apiKey?, baseUrl?, model? } }  // 各家的覆盖项（key 只存本机）
  }
  ```
  旧扁平结构（`llm.baseUrl / model / apiKey`）在 settings 读入时**自动迁移**进 `providers.local`，老配置无缝。
- 产物：本地默认无 key 即可用；各家 key 存 `<userData>/zhijuan-settings.json`（与现状一致）。子进程只把**当前活跃 provider 的 key**以对应环境变量注入，不把全量 key 交给引擎。

### C. 创作上下文装配（主进程，harness 真正注入）

新增 `src/main/agent/context.ts`：`buildWritingContext(projectId, chapterRel)` → `{ blocks, sources }`，只读当前章相关的写作半径，**预算硬控**（沿 ROADMAP M1.3 的「设定 ≤…、前情 ≤…」精神）：

1. 【当前章节】正文（去 front matter，≤8000 字）；
2. 【上一章尾部】同卷上一章的最后 ≈3000 字（承接前情，续写不断片）；
3. 【人物档案】本章 `涉及人物` 每位 ≤4000 字（最多 4 位）；
4. 【世界观切片】`世界观/<切片>.md` ≤4000 字；
5. 【本章章卡】`大纲/<章节名>.md` 若有（一句话定位 / 关键事件 / 钩子 → 写作时记得要还的债）≤2000 字；
6. 【素材库索引】**索引** ≤1200 字（不灌内容，只是路标；要细节仍 zj_* 读）。

read 全部 try/catch——项目缺文件、测试脚本、章节未建都不炸，装配到什么算什么。注入点：
- `runChat`（创作主通道）：系统人设 + 环境块 + **创作上下文块** + 历史 + 引用 + 提问；并在系统侧写明「以下为当前章节与其设定的装配上下文，可直接用；要看更多细节再 zj_* 读对应文件」。
- `runSync`（切片同步）：同样注入（模型有事实在前，仍然允许再用 zj_* 验证），加快且更稳。
- 全卷巡查（audit）与本章小环（chapterCheck）本就是「主进程材料包」骨架，天然带足上下文，不再动。
