## 每轮四阶段契约（全部模块通用，逐轮执行）

1. **调研**：读本模块档案的「下一步计划」「当前状态」+ 权威源（ROADMAP / 模块设计-V2 / 架构评审）本模块章节；围绕本轮主题做**真实上网调研**（web_search / web_extract / 本机无头浏览器 CDP 9224，被拦用 r.jina.ai），来源记 URL，禁止凭记忆编。主题 = 档案候选之一，或本模块自发现。
   **调研方向优先级（主人 2026-09-12 定，刚性口径）**：
   - ① **创作方法论**：叙事结构/章节节奏/人物弧/情绪曲线/类型章法/开篇钩子/读者期待管理/爽点与铺垫——这是要素引擎与导演引擎的**理论输入**，优先；
   - ② **产品形态**：AI 辅助创作的产品范式、同类写作工具（写作软件/AI 小说助手）的功能与工作流、真实创作者的需求与痛点、作者工作流如何被工具承接；
   - ③ **技术规则调研（HIG / CSS / 组件库 / 框架文档）仅为支撑**——仅当议题需要落地具体 UI/技术时做，且必须写明它服务于上面①/②的哪个创作/产品问题；**不作为主题主体**。
   - 主题选择要求：每次必须至少产出「创作/产品视角」的调研结论（哪怕本议题偏技术，也要写清它如何改善作者体验或创作结果）。
2. **产品规划**：调研结论结合产品诉求（人与 agent 协作、要素/导演两条引擎、面向时间切片的设定推进、提案制、正文为源）收敛出**本轮优化点**：为什么现在做、怎么做、涉及哪些文件、不动什么、验收口径——写进档案。
3. **技术落地**：选**小步、一行可验**的一点实现。遵守 zhijuan-app 技能与 ui-ux-pro-max 约定（Prose/Milkdown 编辑器、正文动 zj_edit_doc 修改卡口径、窄窗口不换行、custom 标题栏右留白、纯本地明文可入 git、不引重量级依赖；需要时先上网找现成方案）。
4. **测试验收**：`npm run typecheck && npm run build && npm test` 三道门全绿才 `git commit`（feat:/fix: 中文一行）；涉及交互/模型链路必须**真实跑通**（锁屏下用仓库无头套路 CDP 9224 + out/renderer，或真模型冒烟脚本），不许只凭截图。
5. **落档指引（核心，主人要求）**：收工前把本轮（日期时间、四阶段摘要、提交号、验证结果）追加进本模块档案「迭代日志」；**重写「下一步计划」**（下一轮照它开工，候选按优先级列 1/2/3）；涉及 ROADMAP/模块设计的在对应行标 ✅。长远规划有进展就更新。

## 周交付窗口（2026-09-16 主人拍板：交付点＝每周五固定验收一个确定增量）

- **为什么**：主人反馈「目前这种推进形式无法确定一个准确的交付时间点」——自主推进是持续吞吐模型，无法承诺「某日交付」。机制改为：交付粒度=**周增量**，交付点=**每周五固定**。细则见 `docs/周交付窗口-机制-2026-09-16.md`。
- **每周一 08:00**：主会话从 ROADMAP/反馈清单/各模块候选收敛出**本周增量**（确定范围＋验收口径＋关键路径），写 `docs/周交付/<周次>-<增量名>.md`。
- **周内轮次**：四模块本周只围绕增量工作（契约四阶段不变）；增量外候选登记不动；反馈清单 P1 当场修且计入当周。
- **每周五 20:00**：主会话按增量验收口径执行（三道门＋冒烟＋真机/截图）→ 周交付汇报发织卷反馈群；增量内未完项滚动入下周。
- **周计划优先级高于自主候选**（反馈清单 P1 仍最高）；交付完成=验收口径全过并已随周汇报发出。

最终回复必须包含**结果行 + 下一步行**两行，每行 ≤55 字、总计 ≤110 字：
- 有实做：`完成 <提交号>：一行概括` ＋ 另起一行 `下一步：<一句话，下一轮准备推进什么>`

「下一步」必须与档案「五、下一步计划」一致（下一轮真会照做）——它是主人发现方向不对时干预的依据；详细内容一律只写档案。
