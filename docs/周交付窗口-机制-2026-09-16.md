# 周交付窗口 · 机制（2026-09-16 主人拍板）

> 来源：主人 2026-09-16 反馈「目前这种推进形式无法确定一个准确的交付时间点」，
> 拍板方案：**改周交付窗口——每周五固定验收一个确定增量，交付点天然确定**（F-20260916-01）。
> 本文档是推进体系的权威机制文档；四模块推进器契约（docs/模块推进/README.md）同步接入本机制。

## 一、问题背景（为什么不给「某日交付大版本」）

自主推进（四模块推进器每天 32 轮、每轮自主排活）是**持续吞吐**模型：单轮长尾 40–67 分钟、
主人反馈 P1 插队、真机验收受锁屏等外部条件阻塞——任何「精确到某日的最终交付日」承诺都是假的。
诚实的替代：**交付点变成固定节奏的「周窗口」，交付物变成确定范围的可验证增量。**

## 二、机制定义

1. **周计划（每周一 08:00，主会话出）**：从 ROADMAP / 反馈清单 / 各模块候选清单中选出**一个本周增量**
   （确定范围、可独立验收的功能集，例如「多线模型层贯通 + 时间线页按线分组」），写入
   `docs/周交付/<YYYY-Www>-<增量名>.md`：包含 ①范围（做什么/不做什么）②验收口径（三道门 + 相关冒烟 +
   真机/截图等可执行判定）③关键结果路径。
2. **周内推进（四模块推进器）**：本周轮次**只围绕本周增量**工作（调研→产品规划→技术落地→测试验收契约不变）；
   增量外的候选登记不动（`候选/下一步` 列表），不插队。例外：反馈清单 P1 当场修，且修的内容计入当周增量验收。
3. **周验收（每周五 20:00，主会话）**：按周计划验收口径逐条执行 → 「周交付汇报」发织卷反馈群：
   交付了什么、怎么验证的（提交号/冒烟结果/截图）、增量内未完成项（若有）→ 滚动入下周。
4. **滚动规则**：增量内未完成项 = 下周增量的一部分（不留挂账）；增量间优先级按 ROADMAP/反馈清单排。
5. **交付定义**：一个增量「完成」= 验收口径全部通过并随周汇报发出；**周窗口就是交付点，每周五天然确定**。

- 不推翻：四模块推进器、四阶段契约、三道门、冒烟体系、反馈清单闭环全部保留。
- 新增：docs/周交付/ 目录（周计划 + 验收记录）；README 契约加「周交付窗口」条款；各推进器提示词已引用
  README（自动生效，无需改 cron 提示词；若提示词内联了排期口径则同步）。
- 待办来源不变：反馈清单仍是 P1/P2 优先级权威；模块候选清单仍是推进器「下一步」来源——但周计划优先级高于自主候选。
