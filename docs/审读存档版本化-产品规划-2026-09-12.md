## 一、需求与为什么现在做

- 织卷「结论必落资产」：全卷检查（一致性巡查 / 冷读报告 / 多视角审读）结论自动落盘 `大纲/审读_<类名>.md`（audit.ts，2026-09-09 起）。
- 存档现为**覆盖式**：每类一个文件、重跑即覆盖上一份。审读的核心价值是回答「**上次说过什么、改了吗**」——覆盖式使这个回答不可答：上一份结论随着一次重跑永久消失，主人无法对照「这次的发现是否上次就提过、是否已处理」。
- **本轮实测的关键事实**：`auditToMarkdown` 档头写「每次重跑覆盖本文件，历史版本在 git 可回溯」——但**项目库不是 git 仓库**（`~/Documents/织卷项目库/` 下 5 个项目逐一 `git -C` 核实：均 `not a git repository`）。该话术不实，历史版本实际**无任何回溯途径**。这直接否定了 2026-09-09 落地时「git 可回溯」的假设，是候选 4 的硬证据。
- 大验收（写完中篇且自洽）路径上，「检查→修订→再检查」是常态；无历史=每次检查都从零开始，修订是否闭环无从证明。

## 二、业界形态调研（来源均为真实抓取，2026-09-12）

| 形态 | 代表 | 形态要点 | 结论 |
|---|---|---|---|
| 云侧全量版本历史 | Obsidian Sync（[官方帮助页](https://help.obsidian.md/obsidian+sync/version+history)，r.jina.ai 抓取全文） | 每次变更存为新 entry；版本列表（左）→ 内容（右）→ Restore 恢复；Standard 保留 1 个月、Plus 12 个月、附件 2 周，到期自动删 | 全量版本 + 时间线 + 恢复 + **保留上限** |
| 本地快照 | Obsidian File Recovery（官方帮助 https://help.obsidian.md/plugins/file-recovery，页面为重定向导航、机制以多来源交叉：默认**每 5 分钟一次快照、保留 7 天**） | 纯本地、「时光机」，独立于同步/VCS | 本地场景 = 时间点快照 + 短保留期，防误删 |
| 页面级历史 | Notion（[帮助中心 · 复制删除和恢复内容](https://www.notion.com/zh-cn/help/duplicate-delete-and-restore-content)）：可查看页面变更历史（谁/何时）并恢复过去版本；垃圾箱保留 30 天 | 全量历史 + 恢复入口 | 与 Obsidian 同范式，云端实现 |
| 既有拍板 | 织卷正文版本历史 2026-09-10 已调研 Scrivener Snapshots（手动快照+Compare）/ obsidian-git（git 驱动）/ JetBrains Local History（自动记录+保留上限+**明示非 VCS 替代**）并拍板**自动快照制**（见 `docs/正文版本历史-产品规划-2026-09-10.md` §二/§三） | 写盘前存旧内容；`.zhijuan/history/<rel>/<ts>.md`；每文件 50 版；不依赖 git | **与本需求同构，直接复用** |

**结论**：业界统一范式 = 全量版本逐次留存 + 可见时间线 + 可恢复 + 有保留上限；织卷正文历史已按此落地，「审读报告版本化」不另造体系——把同一机制的适用范围从 `正文/` 扩到审读报告即可（成本 ≈ 几行 + 单测）。

## 三、拍板方案

1. **范围**：仅 4 类审读报告（一致性巡查 / 冷读报告 / 多视角审读；perspectives 与 review/consistency 同走 runAudit 落盘）。**章卡 / 导演板不入**：写作副产物、恢复需求弱、目录噪音；真需要时同一机制再扩（档案记为观察项）。人物/世界观改动走提案制（提案文件本身是审计轨迹），不涉及。
2. **存储**：复用 `history.ts` 全套——`.zhijuan/history/大纲/审读_<类名>/<yyyyMMdd-HHmmss-SSS>.md`（`snapDirFor` 按 rel 去 `.md` 保留层级，天然可用）。
3. **触发**：`store.writeDoc` 挂接处条件 `isNovelRel(rel)` → `isVersionedRel(rel)`（= `正文/` 前缀 ∪ `大纲/审读_` 前缀）；行为不变（目标已存在且内容不同才快照旧内容）。审读报告属低频生成，快照仅在重跑且结果有变化时产生——无空转。
4. **保留份数**：沿用 `HISTORY_LIMIT = 50`（统一口径、零新增配置；全卷检查一天最多数次，50 版 ≈ 一月余量，正文历史同参数已验证）。
5. **档头文案修正**：`auditToMarkdown` 的「历史版本在 git 可回溯」改为「历史版本自动留存于项目内 `.zhijuan/history/`」——先纠不实话术，再谈功能。
6. **UI 入口（二期，一期只做数据层）**：大纲区「审读存档」条目旁加「历史」按钮 → 复用 `HistoryDrawer`（props 同为 `{ projectId, rel }`，零新组件；列表 + 行级 `buildDiffView` + 一键恢复现成）。结构化对比（二期之后）：`shared/auditDiff.ts` 纯函数 `diffAuditReports(prev, next)`——按条目 key（`where+what` 归一）分类 新增 / 已解决 / 依旧（severity 变化单独标注），三计数 + 列表；入口=审读抽屉新 Tab 或报告查看页「与上次对比」。行级 diff 兜底可看原文差异；语义三态才是「上次说过什么、改了吗」的正解。
7. **归属**：生成与版本化数据层=智能层（main/history.ts、store.ts、audit.ts）；入口 UI=大纲区（审读存档展示本就是智能层先例 55eb47f）；体验层只做视觉复审。**先定归属再排实现——已定：一体在智能层**。

## 四、不动什么 / 不做什么

- 不动正文版本历史的既有行为与测试（`isNovelRel` 调用点改为等价的 `isVersionedRel`，正文语义不变）、提案制、切片同步、大纲区目录结构（审读报告仍在 `大纲/审读_*.md`，最新版位置不变——历史在 `.zhijuan/history/`，`listDocs` 已跳过点目录，不污染大纲列表）。
- 不做：设置化（保留份数等默认值先行，与正文史同策略）；章卡/导演板入历史；git 化项目库候选（正文史规划 §三.5 已论证「不依赖 git」，同一结论适用）；手动快照按钮。
- 不引第三方依赖。

## 五、决策点（向主人汇报；均为小到中取舍，若主人无异议按此执行）

1. **是否做**：建议做——审读是「检查→修订」闭环的唯一结论载体，覆盖式 + 非 git 项目库 = 结论不可回查；复用机制成本极低（一期 ≈ 10 行内 + 单测）。
2. **归属**：智能层（数据 + 入口一体，不拆两模块）。
3. **保留份数**：50 版（与正文史同常量）。
4. **章卡/导演板**：本轮不入历史（观察项）。
