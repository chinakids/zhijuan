# M1 要素引擎 · 设计图纸（v1，按主人 2026-08-13 意见升级：设定时间线）

> 目标：**让每一次章节生成，都只带上「这一章需要的」设定、人物状态与前情**（替代整包硬塞），并且**任何设定都以时间线的形式随正文生长**——每个章节阶段一个设定切片，生成时永远取「到本章为止」的最新切片，从机制上避免『啃书啃错』（拿旧版本当现在）。
> 范围：只做生成侧的上下文工程；不动曲线引擎（那是 M2），不动现有作品的目录结构。

## 1. 现状与要解决的腐烂点

1. **设定腐烂**：生成时把全部世界观 + 全部人物整包硬塞 → 长文下设定变噪音；改过的老设定也会被旧的一起带走。
2. **状态腐烂**：人物只有「初始设定」，没有「随着剧情走到现在的状态」。写第 40 章时，LLM 以为她还和第 1 章一样。
3. **版本错乱**：就算有状态，也很难知道「某一刻」她到底是什么样 —— 这正是主人点名要补的：**设定要有时间线，要能看到每个章节阶段的切片，观察人物成长与环境变化，避免啃书啃错**。
4. **前情腐烂**：正文从没进过上下文，前章约定、伏笔、关系推进全忘。

## 2. 核心新概念：设定时间线（Setting Timeline）

> 一句话：**每条设定不是「一个值」，而是一条随时间（按章）演进的切片串。**
> 切片的来源有三：初始设定（作者写的）、随正文沉淀（章节审计时总结出来）、手动调整（作者改的）。

```ts
/** 一个设定切片：某个设定在「第 atChapter 章起」有效的内容 */
interface SettingSlice {
  atChapter: number        // 从这一章起，本切片接管该设定
  content: string          // 本章节阶段的设定正文（够用的完整描述）
  changeLog?: string       // 相对上一切片的变化说明（为什么变了：哪章哪件事）
  source: 'initial' | 'sweep' | 'manual'   // 初始 / 随正文沉淀 / 手动
  confirmed: boolean       // sweep 产生的要先确认才生效
}

/** 通用要素条目卡：一条规则 / 一个场景 / 一件道具 / 一条 lore */
interface Element {
  id: string
  kind: 'rule' | 'scene' | 'prop' | 'lore' | 'other'
  name: string            // 名称，召回主键（如「异能档位」「学校琴房」「专属玻璃杯」）
  tags: string[]          // 召回依据
  slices: SettingSlice[]  // **时间线：slices[0] 为初始设定，之后每章阶段的切片按 atChapter 升序**
  active: boolean         // 停用的条目不再进上下文
  createdAt: number
  updatedAt: number
}

/** Character 同样获得时间线（人物也是会成长的设定） */
interface Character {
  // ……原字段全部保留（name/role/age/fields/tags…)……
  firstAppear?: number
  active: boolean
  slices: SettingSlice[]  // 外观、性格、关系的阶段性切片；含掎档案的变化也在切片里记
}

/** 每章一份的「章节审计」——章节结束时的世界快照（不含设定本体，只含该章发生了什么） */
interface ChapterRecord {
  chapterNum: number
  summary: string                       // 80~150 字事件摘要
  characterStates: { charId: string; state: string }[]  // 出场人物本章末状态（供展示，设变走切片）
  resolved: string[]                    // 兑现的伏笔
  sown: string[]                        // 新埋伏笔
  standingChanges: string[]             // 规则被触发、场景被破坏等永久性变化（提示语，实际落成切片）
}

/** 待确认的沉淀草稿池（sweep 结果，主人接受后才进时间线） */
interface SweepDraft {
  id: string
  targetType: 'element' | 'character'
  targetId: string
  targetName: string
  atChapter: number
  draftContent: string       // 拟新增的切片内容
  changeLog: string          // 变化原因（引正文依据）
  status: 'pending' | 'accepted' | 'edited' | 'rejected'
}

/** 全局伏笔台账（自带时间位置） */
interface Foreshadow {
  id: string
  desc: string
  sownChapter: number
  resolvedChapter?: number
  status: 'open' | 'resolved' | 'dropped'
}

/** 生成时的上下文包（组配器输出） */
interface AssembledContext {
  selectedChars: Character[]            // 每份按「到本章为止」的切片补全，总档案裁剪后 ≤1 份 400 字
  charStatesNow: string[]               // 这些人物在本章的当前状态（取自时间线最新切片，附「自第 N 章」标注）
  elementsNow: Element[]                // 召回的条目，同样取「到本章为止」最新切片（≤8 条，共 ≤1200 字）
  recent: { chapterNum: number; summary: string }[]  // 前情摘要（含衰减）
  openForeshadows: string[]             // 全局未兑现伏笔
}
```

## 3. 三条主流程

### 流程 A：设定维护（「设定库」视图 + 时间线视图）
- 设定库：Element 的增删改、标签、启用/停用；创建时写的就是「初始切片（source=initial）」。
- **时间线视图**：顶部一条章节进度滑块。拖到第 N 章，设定库整体显示为**第 N 章时刻的快照**——每条设定用「到本章为止的最新切片」渲染，并标出「自第 X 章发生变化」。可直观看到人物成长的每个阶段、环境怎么变的。同时也是「避免啃书啃错」的检查手段。
- 每一条目标记：该设定下一步的变化会先落到草稿池，不会直接悄悄改。

### 流程 B：章节结束 → 「随正文沉淀」章节审计（主人手动触发，可编辑可重生成）
1. 对已完成正文的章节点「生成本章记录」，调用本地 LLM **两步走**：
   - 第一步产 ChapterRecord（摘要 / 每人状态 / 兑现与新埋伏笔 / 永久变化）；
   - 第二步做**设定变化检测**：拿着本章正文，对照每个出场设定在**本章之前**的最后切片，输出「疑似变化清单」——哪条设定、变成什么样、依据正文哪段。
2. 变化清单全部进 **SweepDraft 草稿池**（不是直接生效）：成组展示，主人可逐条「接受 / 编辑后接受 / 丢弃」，也可一键接受全部。
3. 接受的条目写入对应设定/人物的时间线成为新切片（source=sweep，atChapter=本章），并把本章记录归档进 project.records，把伏笔台账更新（新埋的 open，兑现的 close）。
4. 主人也可以随时手动在时间线里「插入切片」（source=manual），比如剧情前就要改的设定可以直接提前写好。

### 流程 C：每章生成前 → 组配器（时间旅行查询，本引擎的关键）

**召回策略（v1 用标签+关键词匹配，零新依赖；够用再升级 embedding）**
1. 从 chapter.elements + beats + premise 做名字/标签命中，地图：`character.name` → 该人物；`Element.name/tags` → 该条目。
2. 前情默认栈：上一章 record 全文 + 再上一章只带 summary 首句，随章距指数衰减；若本章要素带「续线」标签（角色名/地名），该线下各章记录全部跟随（越老截取越多）。
3. 未兑现伏笔：**始终附上**，无论召回到哪。

**时间旅行查询（防啃书啃错的核心）**：对每个被召回的人物/条目，取它的时间线里 **`atChapter ≤ 当前章` 的最后一个切片**作为本章设定，并在 prompt 里标注「该设定自第 X 章起为此状态」。**比当前章晚的切片一律不出现** —— 后文才发生的事不会提前泄给前文。

**硬预算（组配器末尾统一压缩）**
- 人物 ≤ 6 个，每份 ≤ 400 字；设定条目 ≤ 8 条共 ≤ 1200 字；前情 ≤ 1000 字；**总上下文增量 ≤ 4000 字** —— 「长文不糊」的闸门。

## 4. 兼容与迁移

- `loadProject` 读旧 JSON 时自动补空集合（elements/records/foreshadows），并把原有 worldview.rules、character.background 等自动包成**初始切片**写进时间线，保证老项目一样能吃时间线；原字段保留。
- 组配器输出为空（老项目、没设任何条目）时**回退全量逻辑**，老体验不变、不回归。
- worldview.rules 等长文本提供「一键沉淀为条目」辅助（把一段文字交给 LLM 拆成多条 Element 草稿进草稿池），不强拆。

## 6. 待主人拍板的小决策

- **D-4 沉淀的确认方式**：随正文沉淀出的变化切片，全部走「草稿池 → 主人逐条或一键接受」再生效（推荐：设定改动的责任在主人，可防 AI 悄悄改设定）；还是设定类自动生效、只把人物状态类进草稿？（自动更多但可能引入主人不想要的设定）
- **D-5 时间线要不要可回滚**：给定一个切片可「退回到旧切片」的操作吗（写歪了能回到第 N 章的样子）？（推荐要，成本低，配合 git 双保险）
- **D-6 章节滑块要不要联动正文**：拖时间线滑块时，顺带把对应章节的正文摘要也显示在设定库旁，方便边看边核对？（推荐要，纯展示不存）
