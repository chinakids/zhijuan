# M1 要素引擎 · 设计图纸（v0，待主人过目）

> 目标：**让每一次章节生成，都只带上「这一章需要的」设定、人物状态与前情**，替代现在「整包硬塞」，从根上解决长文后期『啃书』（失忆、设定过时、伏笔烂尾）。
> 范围：只做生成侧的上下文工程；不改现有作品的目录结构，不动曲线引擎（那是 M2）。

## 1. 现状与要解决的三个腐烂点

1. **设定腐烂**：生成时把全部世界观 + 全部人物整包塞进去 → 长文下设定变噪音，重点被稀释；人物设定改了也能被旧的一起带走。
2. **状态腐烂**：人物只有「初始设定」，没有「随着剧情走到的现在的状态」。写第 40 章时，LLM 以为她还和第 1 章一样。
3. **前情腐烂**：正文从没进过上下文。前章的约定、伏笔、关系推进，第 N 章全忘。

## 2. 新增数据模型（项目仍是单 JSON，纯本地）

```ts
/** 通用要素条目卡：一条规则 / 一个场景 / 一件道具 / 一条 lore */
interface Element {
  id: string
  kind: 'rule' | 'scene' | 'prop' | 'lore' | 'other'
  name: string          // 名称，召回主键（如「异能档位」「学校琴房」「专属玻璃杯」）
  tags: string[]        // 召回依据（如「学校」「圈子」「道具」）
  content: string       // 设定正文
  active: boolean       // 停用的条目不再进上下文
  version: number       // 每次修改递增，能看清设定演化
  createdAt: number
  updatedAt: number
}

/** 每章一份的「章节审计」——章节结束时的世界快照 */
interface ChapterRecord {
  chapterNum: number
  summary: string                                    // 80~150 字事件摘要
  characterStates: { charId: string; state: string }[] // 出场人物各自章节末状态
  resolved: string[]       // 本章兑现的伏笔（描述）
  sown: string[]           // 本章新埋的伏笔（描述）
  standingChanges: string[] // 打动世界观的永久性变化（关系、异能档位、地点状态）
}

/** 全局伏笔台账（跨章节） */
interface Foreshadow {
  id: string
  desc: string
  sownChapter: number
  resolvedChapter?: number
  status: 'open' | 'resolved' | 'dropped'
}

/** Character 只加三个字段：首现章、是否存活启用、参与度（保留独立类型，不改成 Element） */
firstAppear?: number
active: boolean

/** Project 追加三个数组（各章节图表的数据全部从这里来） */
elements: Element[]
records: ChapterRecord[]
foreshadows: Foreshadow[]
```

## 3. 三条主流程

### 流程 A：设定维护（补充「设定库」视图）
- 新增「设定库」页：Element 的增删改、标签、启用/停用。人物仍在「人物」视图维护（不加进条目）。
- 章节的「本章要素」保持主人现在的自由文字输入框；旁边提供「从设定库点选本章要素」的辅助（点选只生成标签引用，不要求主人改写面文）。

### 流程 B：章节结束 → 生成「章节审计」（手动按钮，为主人可控）
- 章节标 done（或点按钮）后，可「生成本章记录」：调用本地 LLM，按固定结构产出 ChapterRecord（summary / 每人状态 / 兑现了哪些伏笔 / 新埋了哪些 / 永久变化），**可编辑可重生成**，确认后落入项目。
- 同时把「新埋伏笔」自动追进全局伏笔台账，把「兑现伏笔」标记 close。
- 为什么不自动跑：写完一章本来就是主人自己的一个确认节点，走一步叫一步更符合他的习惯；也省得每章多一次神秘 LLM 调用。

### 流程 C：每章生成前 → 组配器（本引擎的关键）
`generator.generate` 内部先走组配，产出 **AssembledContext** 再拼 prompt：

```ts
interface AssembledContext {
  selectedChars: Character[]     // 全档案（每份裁剪后 ≤400 字）
  charStates: string[]          // 这些人物最新的状态快照（来自 records）
  elements: Element[]           // 本次召回到的条目（≤8 条，共 ≤1000 字）
  recent: { chapterNum: number; summary: string }[]  // 前情摘要（含衰减）
  openForeshadows: string[]     // 全局未兑现伏笔清单
}
```

**召回策略（v1 用标签+关键词匹配，零新依赖；够用再升级 embedding）**
1. 从 chapter.elements + beats + premise 里做名字/标签命中：命中 `character.name` → 全档案 + 最近状态；命中 `Element.name/tags` → 拉条目。
2. 前情默认栈：上一章 record 全文（summary + 被选人状态）+ 上上章只带 summary 首句；随章距**指数衰减**。
3. 若本章要素含有「续线」标签（如某个角色名、地名），把该线下历史章记录全部跟随（老的截取更多）。
4. 未兑现伏笔：不管召回到哪，**始终附上**（voluntary）。

**硬预算（在组配器末尾统一压缩，防止长文时悄悄膨胀）**
- 人物 ≤ 6 个（超出按命中分排序截断）；每人物档案裁剪后 ≤ 400 字
- 设定条目 ≤ 8 条共 ≤ 1000 字；前情（含衰减）≤ 1000 字
- **总上下文增量 ≤ 4000 字**，其余一律不带 —— 这就是「长文不糊」的闸门

## 4. 兼容与迁移

- `loadProject` 读到旧 JSON 时自动补空 `elements: [] / records: [] / foreshadows: []`，原字段全保留。
- 组配器输出为空时（老项目、没用设定库），**回退到现在的全量逻辑**，保证老体验不变、不回归。
- worldview.rules / background 等大文本，提供「一键沉淀为条目」辅助按钮（把一段文字交给 LLM 拆成多条 Element 草稿），但**不强拆**，主人可留着原样。

## 5. 落地顺序（每步都可验证，随时可停）

| 步 | 内容 | 验收 |
|---|---|---|
| 0 | 数据模型加字段 + 迁移 + 设定库视图（Element CRUD） | 老项目打开无异常，可新增条目并保存 |
| 1 | 组配器 + generator 改造（带兜底回退） | 新项目生成结果与改前相当；有设定库时上下文不再全量 |
| 2 | 章节审计 + 伏笔台账 + 生成时附未兑现伏笔 | 写完一章生成记录，下一章 prompt 带出它和未兑现伏笔 |
| 3 | 「沉淀为条目」辅助 + 用一个真实中篇跑通 5 万字前后自洽 | 第 40 章能正确引用第 3 章的伏笔与状态 |

## 6. 待主人拍板的小决策

- **D-1 章节审计的触发**：做成按钮由主人手动「生成本章记录」，还是每章完成后自动就跑？（我建议手动，可编辑，符合你各节点确认的习惯）
- **D-2 历史深度**：默认只带上一章全文 + 更早衰减；要不要支持写某章时**手动钉住**任意历史章一起带上（当你心里有明确要回填的伏笔时用）？（我建议要，成本小）
- **D-3 设定库的范围**：要不要顺带把你的《创作规范》式「约定」（如某类套路轮换、生效规则）也作为开关条目放进去，还是只放剧情相关？（建议先只放剧情相关，规范走你自己的文档）
